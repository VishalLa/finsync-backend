# FinSync backend

demo link:- https://bank-rec-frontend.vercel.app

The FinSync backend is a Flask API for bank reconciliation, bill processing, ledger reporting, TDS, and GSTR-1 workflows. Long-running reconciliation, OCR, and report work is run by Celery with Redis; PostgreSQL stores application data.

## Components

| Component | Responsibility |
| --- | --- |
| `api/` | Flask blueprints and request validation |
| `service/` | The only PostgreSQL client; DB RPC, persistence, reports, and legacy DB workflows. Bank reconciliation workbooks are generated by `service/reports/bank_recon_xlsx.py`. |
| `matcher/` | Exact, fuzzy, memory, AI-assisted, and residual reconciliation stages |
| `entry_point/` | Bank/ledger file loading and the opt-in OCR worker app |
| `ledger/` | Journal, general-ledger, TDS, and GSTR-1 domain logic |
| `database/` | SQLAlchemy models, database manager, and authentication models |
| `schema/` | Domain data structures used by the pipelines |
| `app/shared/` | Queue messages, settings, storage, Celery factory, rate limiting, and reconciliation run quota |

The matcher and ledger packages have their own implementation notes: [matcher/README.md](matcher/README.md) and [ledger/README.md](ledger/README.md).

## Architecture

```text
Client
  │ JWT-authenticated HTTP requests
  ▼
Flask API (`api/`)
  ├── synchronous DB requests ──► Redis RPC ──► service worker
  └── queued work ──────────────► Redis queues
                                     ├── entry_point worker
                                     ├── matcher worker
                                     └── service worker
                                           │
                                           ▼
                                      PostgreSQL

Optional local services: PaddleOCR processes uploaded bills; Ollama is used by the AI matching stage.
```

For bank reconciliation, the queued stages are currently:

```text
API upload
  -> entry.process_run       parse ledger and bank files
  -> db.store_inputs         create the run and persist parsed rows
  -> matcher.run             reconcile the normalized rows
  -> service.save_results    build the reconciliation workbook
  -> db.store_results        persist matches, audit rows, and final status
```

Queue messages contain the run/user IDs and references under `STORAGE_DIR/runs/<run_id>/`; raw files and normalized/results JSON stay in shared storage rather than being sent through Redis. The database-input stage intentionally finishes before matching starts so match rows can reference persisted ledger and bank rows. The API, entry, and matcher processes do not import database code or receive database credentials. All consumers must share the same storage volume; use shared object storage before placing workers on separate hosts.

## Requirements

- Python `>=3.10,<3.13` (the Docker image uses Python 3.11)
- PostgreSQL
- Redis
- Optional: Ollama with the configured model for AI-assisted matching
- Optional: Docker and Docker Compose for the containerised stack

Dependencies are declared in `pyproject.toml`; `req.txt` is used by the Docker image.
`bcrypt` is pinned to `4.0.1` for compatibility with the current `passlib` password-hashing backend.

## Configuration

Create `Backend/.env`. `Config` loads it at startup.

```dotenv
# Use DATABASE_URL, or provide the full POSTGRES_* set below.
DATABASE_URL=postgresql://finsync:change-me@localhost:5432/finsync
# POSTGRES_USER=finsync
# POSTGRES_PASSWORD=change-me
# POSTGRES_HOST=localhost
# POSTGRES_PORT=5432
# POSTGRES_DB=finsync

REDIS_URL=redis://localhost:6379/0
SECRET_KEY=replace-with-a-long-random-value
JWT_SECRET_KEY=replace-with-a-different-long-random-value

# Email verification (required when an unverified user attempts to log in)
EMAIL_USER=your-smtp-account@example.com
EMAIL_PASS=your-smtp-app-password
EMAIL_OTP_SALT=replace-with-a-random-value
# Optional SMTP and verification-link overrides
EMAIL_SMTP_HOST=smtp.gmail.com
EMAIL_SMTP_PORT=587
EMAIL_VERIFICATION_URL=http://localhost:8000/auth/verify-email

# Optional
CORS_ALLOWED_ORIGINS=*
OLLAMA_URL=http://127.0.0.1:11434
OLLAMA_NAME=phi3:latest
STORAGE_DIR=storage
POOL_WORKERS=1
```

`DATABASE_URL` takes precedence when it is a PostgreSQL URL. A SQLite URL is accepted for local development, but PostgreSQL is the supported database. `STORAGE_DIR` is created automatically and holds uploaded files and generated reports. In containers, the default storage path is `/data/uploads` and the default Ollama host is `ollama`.
Access tokens are valid for 12 hours. Generated reports are stored under `STORAGE_DIR/reports`, which must be on shared storage mounted by both the API and Celery worker.
`CORS_ALLOWED_ORIGINS` accepts `*` to allow any origin or a comma-separated list of origins, such as `http://localhost:5173,https://bank-rec-frontend.vercel.app`. Set it to the frontend's exact origin (scheme and hostname, no trailing slash) and restart/recreate the API container; an unset or blank value disables cross-origin requests. Docker Compose passes this setting explicitly to the API without exposing database credentials.
On startup, the backend adds the `email_verified` column to an older `user` table if needed. Existing accounts are marked verified so this schema upgrade does not lock them out.
Ledger IDs are unique within a reconciliation run, rather than across the entire database. On startup, the backend migrates the older global `ledger_id` constraint for PostgreSQL and SQLite databases.

## Rate limiting and reconciliation quota

The API uses Flask-Limiter with a sliding-window counter. A global limit applies to every route by client IP; `/` and `/healthz` are exempt. Authenticated tier limits use the JWT identity, falling back to the client IP when no valid identity is available.

| Tier | Default limit | Identity | Applied to |
| --- | --- | --- | --- |
| `default` | 200 per minute | Client IP | All routes, except `/` and `/healthz` |
| `auth` | 5 per minute | Client IP | Registration, login, and email verification |
| `heavy` | 10 per hour | JWT identity, or IP fallback | Reconciliation and bill uploads, full runs, report generation, and account deletion |
| `normal` | 60 per minute | JWT identity, or IP fallback | Ordinary API reads and actions |
| `poll` | 120 per minute | JWT identity, or IP fallback | Reconciliation, bill, pipeline, and report status polling |

Each limit can be changed with its matching `RATELIMIT_*` environment variable. The limiter uses the Redis URL from `REDIS_URL` with its database path changed to `/1` by default. Set `RATELIMIT_REDIS_URL` to override that URL, or `RATELIMIT_REDIS_DB` to choose a different database index. The default Redis database used by Celery is not changed.

Normal routes fail open when Redis is unavailable. Registration, login, and email-verification routes fail closed with a JSON `503` response and `Retry-After: 5`. Rate-limit `429` responses use the API's JSON error format and include `Retry-After` and `X-RateLimit-*` headers; those headers are exposed to browser clients when CORS is enabled.

The API also limits each user to three active reconciliation submissions by default (`MAX_ACTIVE_RUNS_PER_USER`). Redis tracks active runs for up to `ACTIVE_RUN_TTL_SECONDS` (default 7200); quota checks fail open if Redis is unavailable. A run's quota is released if submission fails. Releasing it when a run completes, fails, or is deleted remains a phase-two follow-up.

See [`.env.example`](.env.example) for the rate-limit and quota defaults. The report workbook implementation now lives only in `service/reports/bank_recon_xlsx.py`, and service callers import it from that module.

For Docker Compose, use container hostnames in `.env`:

```dotenv
POSTGRES_USER=finsync
POSTGRES_PASSWORD=change-me
POSTGRES_DB=finsync
POSTGRES_HOST=postgres_db
POSTGRES_PORT=5432
REDIS_URL=redis://redis_server:6379/0
SECRET_KEY=replace-with-a-long-random-value
JWT_SECRET_KEY=replace-with-a-different-long-random-value
```

## Run locally

From `Backend/`:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r req.txt

# Start PostgreSQL and Redis, then configure .env as above.
python manage_db.py
python main.py
```

In another terminal, with Redis, PostgreSQL, and the same storage configuration:

```bash
celery -A entry_point.celery_app:celery_app worker --loglevel=info --queues=entry_point.queue
celery -A matcher.celery_app:celery_app worker --loglevel=info --queues=matcher.queue
celery -A service.celery_app:celery_app worker --loglevel=info --queues=service.queue,db_storage.queue
```

The service worker handles synchronous API-to-database RPC and all retained DB-backed Celery tasks. `manage_db.py` applies the additive run association columns used for per-run ignored/audit records.

The Flask development server listens on `http://localhost:8000`.

To enable the optional AI matching stage locally:

```bash
ollama pull phi3:latest
ollama serve
```

## Run with Docker Compose

Add the Docker configuration values above to `Backend/.env`, then run:

```bash
docker compose -f docker-compose.microservices.yml up --build
```

Compose builds separate API, entry, matcher, and service images. Only the service image receives database credentials. The legacy worker is retained for unmigrated queues; OCR remains opt-in under the `next` profile. The API is exposed on port `8000`.

Pull the model once the Ollama container is healthy:

```bash
docker compose -f docker-compose.microservices.yml exec ollama ollama pull phi3:latest
```

## API overview

All routes other than registration and login require `Authorization: Bearer <token>`.

| Area | Routes | Notes |
| --- | --- | --- |
| Authentication | `POST /auth/register`, `POST /auth/login`, `GET /auth/verify-email?token=...`, `POST /auth/logout`, `GET /auth/me`, `DELETE /auth/delete` | An unverified user receives a verification link on login and cannot obtain a JWT until verified. Registration requires `password`, `first_name`, `phone_no`, and `email`. |
| Reconciliation | `POST /api/bank-rec/reconciliation` | Multipart upload with `ledger_file` and `bank_file`; both must be CSV or XLSX. Returns a Celery task ID. |
| Reconciliation status/results | `GET /api/bank-rec/reconciliation/<run_id>/status`, `GET /api/bank-rec/reconciliation/<run_id>` | Poll task state, then read persisted reconciliation results. |
| Saved reconciliation runs | `GET /api/bank-rec/previous/runs/<user_id>`, `GET /api/bank-rec/previous/runs/<user_id>/<run_id>`, `DELETE /api/bank-rec/previous/runs/<user_id>/<run_id>` | JWT identity must match `user_id`. Deletion removes the run's reconciliation rows and stored input/report files; posted journal entries are retained but detached from the deleted run. Processing runs cannot be deleted. |
| Reconciliation follow-up | `POST /api/bank-rec/reconciliation/<run_id>/report`, `POST /api/bank-rec/reconciliation/<run_id>/journal-entries/approve` | Queue a run report or approve a non-empty `entries` list. |
| Bills | `POST /api/pipeline/bills`, `GET /api/pipeline/bills/<bill_id>/status` | Submit multipart `file` (`png`, `jpg`, `jpeg`, or `pdf`) or multipart `raw_data` JSON. `direction` is `input` or `output`. |
| Bill-to-bank full run | `POST /api/pipeline/fullrun`, `GET /api/pipeline/tasks/<task_id>` | Upload bill files and a bank statement together. The worker extracts and stores the bills, builds their bank-facing ledger rows, then runs reconciliation. |
| GSTR-1 pipeline | `POST /api/pipeline/gstr1`, `GET /api/pipeline/tasks/<task_id>` | Requires `period_label`, `period_start`, and `period_end`. |
| Ledger | `GET /api/ledger/trial-balance?as_on=YYYY-MM-DD` | Returns the trial balance for the requested date. |
| Reports | `POST /api/reports/{bank-reconciliation,gstr1,journal,ledger,tds}` | Queues an Excel report. Use `GET /api/reports/tasks/<task_id>` to poll and `GET /api/reports/tasks/<task_id>/download` to download it. |

Report request fields:

| Endpoint | Required JSON fields |
| --- | --- |
| `/api/reports/bank-reconciliation` | `run_id` |
| `/api/reports/gstr1` | `period_label` |
| `/api/reports/journal` | `date_from`, `date_to` (`YYYY-MM-DD`) |
| `/api/reports/ledger` | `as_on` (`YYYY-MM-DD`) |
| `/api/reports/tds` | `period_start`, `period_end` (`YYYY-MM-DD`) |

### Bill-to-bank full run

`POST /api/pipeline/fullrun` is a multipart endpoint for the end-to-end flow.
Send one or more bill files under `bill_files` and a CSV or XLSX statement
under `bank_statement` (the aliases `bills` and `bank_file` are also
accepted). Bill files may be `png`, `jpg`, `jpeg`, or `pdf`.

```bash
curl -X POST http://localhost:8000/api/pipeline/fullrun \
  -H "Authorization: Bearer <token>" \
  -F "bill_files=@purchase-invoice.jpg" \
  -F "bill_files=@paid-expense.pdf" \
  -F "bank_statement=@statement.xlsx"
```

The response is `202 Accepted` and includes `task_id`, `run_id`, and a
`status_url`. Poll `GET /api/pipeline/tasks/<task_id>` until it succeeds.
The completed result includes each bill's processing result, the count of
bank-reconcilable ledger rows created from its persisted journal entries, and
the normal reconciliation summary/report links. Only bills with a Cash or
Bank journal posting produce rows that can be matched to the statement.

## Background work

Celery uses Redis for both broker and result backend. Worker apps are declared with their domain packages:

- `entry_point.celery_app`: file parsing and handoff to the service.
- `matcher.celery_app`: reconciliation and handoff to the service.
- `service.celery_app`: DB persistence, synchronous API RPC, bills, reports, and full-run workflows.
- `ledger.celery_app`: reserved for ledger-specific worker tasks; DB-dependent ledger operations remain in `service`.

Only the service worker receives PostgreSQL credentials. The API uses Celery result RPC for DB-backed operations, and workers share the same Redis and storage volume.

## Operational notes

- `main.py` is a development entrypoint. Run the Flask app behind a production WSGI server for deployment.
- Persist `STORAGE_DIR` in production; report downloads depend on the generated file still being available there.
- Replace all example credentials and secrets. Do not expose PostgreSQL or Redis ports outside a trusted network.
- Set `CORS_ALLOWED_ORIGINS` to the browser app's origin(s) when it is hosted separately from the API. Use `*` only when intentionally allowing every origin.
